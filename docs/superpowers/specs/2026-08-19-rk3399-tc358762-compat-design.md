# RK3399 TC358762 Compatibility Driver Design

**Date:** 2026-08-19  
**Status:** Approved in chat; hardware implementation pending

## Problem

The original Raspberry Pi 7-inch Touch Display is detected on the Rock Pi
4B+, its ATTINY88 controller responds at I2C address `0x45`, its backlight is
powered at full brightness, its FT5426 touch controller works at `0x38`, and
DRM exposes an enabled 800x480 `DSI-1` connector. The screen nevertheless
shows only a lit black panel.

The kernel records eleven `dw-mipi-dsi-rockchip ... failed to write command
FIFO` errors whenever DSI is enabled. The upstream
`panel_raspberrypi_touchscreen` driver programs the TC358762 bridge during
panel `prepare()`, before the RK3399 DesignWare DSI host can accept those
transfers on this machine. Radxa's working downstream driver instead programs
the bridge during panel `enable()`. Desktop layout changes reproduce the same
errors and cannot fix the panel.

An earlier overlay defect that enabled unused DSI0 prevented the entire
Rockchip DRM master from binding and took HDMI down. That defect is already
fixed: DSI0 remains disabled and DSI1 is the only DSI output component.

## Goals

- Produce video on the original 800x480 Raspberry Pi Touch Display.
- Preserve the working HDMI output and its existing Xorg configuration.
- Preserve the working five-contact FT5426 polling input driver.
- Keep installation, upgrade, uninstall, and offline recovery transactional.
- Carry complete upstream and Radxa attribution.
- Keep hardware claims pending until panel, touch, HDMI, reboot, and cold-start
  checks pass.

## Non-goals

- Support Raspberry Pi Touch Display 2 or unrelated panels.
- Patch the generic Rockchip DSI host.
- Import Radxa's full legacy MCU, touch, and display stack.
- Change desktop monitor placement or touch calibration in the kernel.

## Architecture

Add a project-owned GPL-compatible module named
`panel_rockpi_rpi_touchscreen`. Its I2C driver binds only to the new compatible
string `rockpi,rpi-7inch-touchscreen-panel` at address `0x45`, preventing the
built-in upstream panel driver from binding to this board-specific path.

The driver owns the complete panel lifecycle:

1. Probe verifies the ATTINY88 identity over I2C before registering anything.
2. Probe registers a one-lane RGB888 MIPI DSI peripheral and a DRM panel with
   the fixed upstream 800x480, approximately 60 Hz mode.
3. `prepare()` powers the panel through the ATTINY88 and waits for its ready
   indication, but sends no DSI bridge commands.
4. `enable()` programs the TC358762 through generic DSI writes using Radxa's
   proven RK3399 sequence, then enables full backlight through I2C.
5. `disable()` turns off the backlight.
6. `unprepare()` powers down the panel.
7. Remove and shutdown paths synchronously disable and unprepare the panel and
   detach/unregister the DSI peripheral without double-freeing managed state.

The mode uses one DSI lane, `MIPI_DSI_FMT_RGB888`, and Radxa's proven video
burst plus low-power command flags. The driver checks and propagates every
I2C and DSI error instead of advertising a successfully enabled panel after a
failed bridge initialization. A DRM backlight device exposes brightness
through the existing ATTINY88 PWM register.

## Device tree

The existing overlay remains DSI1-only and continues routing the little VOP to
DSI1. Only the panel compatible changes from
`raspberrypi,7inch-touchscreen-panel` to
`rockpi,rpi-7inch-touchscreen-panel`. Panel address `0x45`, touch address
`0x38`, the reciprocal DSI graph, and HDMI state remain unchanged.

Validation must reject:

- enabled DSI0;
- the upstream Raspberry Pi panel compatible on this RK3399 route;
- a missing or wrong project panel compatible;
- incorrect I2C addresses, mode size, VOP route, or disabled HDMI.

## DKMS and installation

Bump the package from `0.1.1` to `0.2.0` because its immutable DKMS contents
change. DKMS builds and installs two modules:

- `raspits_ft5426`
- `panel_rockpi_rpi_touchscreen`

The source allowlist gains only the new panel source and any focused shared
header. Installer verification compares the built and installed checksum of
both modules, verifies both metadata/aliases, and verifies the DTBO checksum.
Migration installs and verifies `0.2.0` before removing the owned `0.1.1`
release. Any failure retains or restores the previously working release,
DTBO, boot configuration, and exact recovery paths. Uninstall removes both
modules through the single DKMS package and never deletes source after a
genuine DKMS removal failure.

## Testing

Development follows RED/GREEN TDD:

- portable/source-level lifecycle tests assert identification-before-
  registration, no DSI writes in `prepare()`, DSI writes before backlight in
  `enable()`, propagated transfer failures, and shared shutdown cleanup;
- warning-enabled builds compile both modules against the running kernel;
- metadata tests require the new OF alias and GPL-compatible license;
- overlay and validator tests require DSI0 disabled, the project compatible,
  DSI1 routing, the two I2C nodes, 800x480, and HDMI unchanged;
- sandbox installer tests cover two-module checksum verification, immutable
  same-version rejection, `0.1.1` to `0.2.0` migration, rollback, and scoped
  uninstall;
- documentation tests keep wiring, SSH/offline rollback, and hardware-pending
  language accurate.

Before boot mutation, run the full repository suite and strict offline
validation. Install only through `scripts/install.sh` and confirm the protected
HDMI Xorg file hash is unchanged.

## Hardware acceptance

With HDMI attached, reboot once and require:

- Rockchip DRM binds HDMI and DSI1 without DSI command-FIFO errors;
- DSI1 reports connected, enabled, and 800x480;
- the panel displays a desktop image and exposes working brightness;
- the FT5426 input device reports touch;
- HDMI remains usable at its intended 1024x600 DFRobot mode;
- touch can be mapped to DSI1 in userspace without changing kernel data;
- a complete power-off/cold-start repeats the result.

Only after those checks pass may the draft PR claim hardware support.

## Recovery

If the next boot regresses either display, use SSH to run the scoped uninstall
or remove only the project overlay token. Offline recovery operates on a
mounted system root as already documented. HDMI's Xorg configuration is never
modified by this work.
